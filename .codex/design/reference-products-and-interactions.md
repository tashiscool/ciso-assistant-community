# Regovise execution UX: reference products and interaction proposal

Research date: **2026-10-11, America/New_York**. Scope: public official Vanta, RegScale and Paramify documentation/product material, plus the Regovise source map already completed in this repository. Audience: analysts, ISSOs, system/control owners, reviewers and assessors operating authorization work. This is a design proposal, not an implemented capability or a finding about the vendors' private applications.

## Research boundary and core direction

No competitor account, production dashboard, private document or credential was accessed. Documented workflows below are vendor-authored evidence of intended behavior; they were not independently exercised. Marketing outcomes, speed claims, certification promises and OSCAL conformity claims were not independently validated. Plan/add-on/preview restrictions matter: Vanta describes rollout and plan differences, RegScale labels several advanced features Enterprise Edition, and Paramify distinguishes some Cloud/AI and self-hosted workflows. Public docs can lag individual product releases.

The proposed Regovise experience combines **Vanta's short path from attention to action**, **RegScale's explicit system/control/assessment structure**, and **Paramify's reusable implementation narrative model**. These are design inferences from the cited workflows, not a claim that one product is universally simpler or better. The product should let an ISSO answer four questions from one system context: What changed? What is due? What proves the implementation? What decision is still required?

Authorization remains a recorded human decision. NIST describes the Authorize step as senior-official accountability for accepting system or common-control risk; the package includes system plans, assessment results and POA&Ms. A green dashboard or successful automation run is insufficient to label a system authorized. [NIST Authorize step](https://csrc.nist.gov/projects/risk-management/about-rmf/authorize-step).

## Regovise's differentiating execution model

The full suite should keep one operational context while exposing the right amount of detail for the current task. A workspace-wide queue answers “what needs my attention”; a system workspace answers “what must happen for this boundary”; a control workspace answers “what satisfies and verifies this requirement”; a package answers “which reviewed versions are being submitted.” Navigation should preserve that chain, not require repeated re-selection of domain, system, assessment and date window.

These proposed interactions reuse current screen families where possible. New durable states, inheritance rules, package snapshots, identity rules, scheduling and authorization behavior require separately approved implementation slices; this report does not change those rules.

### Persistent system and scope context

Keep the selected domain and system visible in the header when entering system work. The header includes system name, boundary identifier, baseline/profile version, accountable owner and authorization decision state. Context switching is an explicit selector; changing a domain/system confirms what will be filtered and does not silently carry draft content to another tenant or boundary.

Default analysts to their permitted work queue; default ISSOs to their system portfolio or last saved permitted system view. A cross-system queue is explicitly labeled **All accessible systems**. External responders receive assignment context and the minimum linked requirement/evidence context, with no admin navigation. A UI role lens must never add permissions beyond backend authorization.

The system workspace uses stable tabs: Overview, Controls, Evidence, Assessments, Risks & POA&Ms, Documents & Package, Monitoring, Activity. Complementary supplier/privacy/continuity relationships appear in overview and contextual drill-ins, then retain their own full workspaces. Program-wide reporting remains accessible outside a specific system.

### Distinct state axes

The proposal uses separate state fields because each answers a different decision. UI can show one primary queue reason and reveal the complete state in detail, rather than put five pills in every row.

| State axis | Proposed values/meaning | Who can establish it |
| --- | --- | --- |
| Work | Not started, In progress, Blocked, Complete | Permitted owner/workflow; completing work does not establish assessment success. |
| Implementation | Not implemented, Partial, Implemented, Planned, Not applicable | Permitted implementation owner/reviewer, with reason/scope. Inherited or hybrid is a separate responsibility/origination attribute. |
| Evidence lifecycle | Draft, Submitted, Changes requested, Accepted, Superseded | Explicit versioned evidence review. Accepted means accepted for a stated purpose/scope, not globally sufficient forever. |
| Test/assessment result | Not assessed, Satisfied, Other than satisfied, Not applicable, Unable to determine | Declared assessment method and result; automatic checks identify their rules and limits. Exact vocabulary can vary by selected assessment profile. |
| Freshness/coverage | Current, Review due, Stale, Unknown; full/partial/unknown population coverage | Derived from stored observation window/cadence/scope completeness. Unknown remains visible. |
| Document review | Draft, Ready for review, Changes requested, Approved version | Version-specific internal document decision. Material changes require another review. |
| Package | Draft, Validation needed, Ready for review, Reviewed snapshot, Submitted, Returned | Snapshot-level package workflow, with clear recipients and validation profile. |
| Authorization | No decision, Under review, Authorized, Conditions recorded, Denied, Expired/Revoked as applicable | Authorized decision actor plus source decision record and terms. This must not be inferred from percentage complete. |
| Execution | Planned/Preview, Queued, Running, Completed, Completed with gaps, Failed, Cancelled | Run receipt established by actual execution; Preview is visibly distinct from collection or writeback. |

This is a proposed vocabulary for implementation design. It must be reconciled with current service enums and program-specific terms, not substituted into persistence wholesale.

## Interaction specifications

### 1. Work queue: one attention item, one clear next step

Provide views **My work**, **Needs review**, **Overdue**, **Evidence expiring**, **Unassigned**, **Blocked**, and system-specific variants. Counts use accessible scope and explicit denominators; they open the corresponding filtered table. The primary table columns are Item, System, Reason/State, Owner, Due/Review date, Last relevant change, Next action. Optional columns include source, risk, control, assessment and evidence freshness. Queue rows retain stable record IDs and source object type; consolidating an issue and its tasks must not create multiple apparent findings.

Selecting a row opens a right-side context panel with the exact requirement or request, last relevant version, evidence summary, blocker and accountable owner. The primary action changes by item: Assign owner, Review narrative, Collect evidence, Resolve failing resources, Respond to request, Review change, Retest, or Inspect package blocker. “Open record” remains a secondary action when the task requires the full workspace.

Returning to the queue preserves filters, sort, page, selected row and scroll position. Review-next navigates within the filtered set, showing the remaining count. Bulk selection clearly states **Selected 12 on this page** versus **All 148 matching this view**; preview lists eligible/ineligible records and reasons. Bulk owner/due-date changes can use a compact review with undo where safe; approval, external sharing, inheritance and status changes with audit consequences require an explicit scoped review.

An empty personal queue says there is no assigned work in the selected scope and offers relevant permitted discovery. Empty search says no matches and offers Clear filters. Service failure preserves the last successfully loaded data with an age label and Retry; it never invents a zero count or a fresh green state. Permission failure explains the unavailable object without disclosing hidden record data.

**Current fit:** `/tasks` already consolidates tasks/validation; `/workbench` and `/assurance/reviews` supply adjacent operational data. Their current local filters are not durable saved views or a complete cross-domain review model. The shared task register is `/modules/tasks`. [Work Queue](/Users/tkhan/IdeaProjects/ciso-assistant-community/.codex/maps/frontend-extended.md), [Task component](/Users/tkhan/IdeaProjects/ciso-assistant-community/apps/web/src/features/ops/TaskAndMappingControlPages.tsx:54), [Workbench](/Users/tkhan/IdeaProjects/ciso-assistant-community/apps/web/src/features/ops/WorkbenchControlPage.tsx:10).

### 2. Control workspace: source requirement and implementation together

Use a readable control list with family grouping, scoped owner, implementation state, assessment result, evidence coverage/freshness, inheritance origin and next action. Clicking a control opens a workspace with a collapsible requirement pane and working implementation pane; the requirement text remains available during authoring/review. Show catalog ID, control/part IDs, edition/version and tailored/profile guidance separately. The user can change controls without losing the selected system or assessment context.

The working area offers Implementation, Evidence, Assessment, Risks/POA&Ms and History. Implementation supports control parts/objectives, organization-defined parameters, responsibility/origination and one or more referenced components/capabilities. Existing source statements stay visible beside draft edits. Every relevant narrative statement can answer who performs it, what is used, how it operates and when it is performed; the UI should offer structured references without forcing all prose into rigid fields.

Evidence rows identify the version, source, observation window, covered resource population, linked parts/objectives and acceptance purpose. Assessment records the method, procedure/criterion, sampling/population, assessor/date, result and justification; automated test results are available as supporting observations rather than replacing the assessor's judgment.

**Current fit:** security-controls/security-plans/components are largely flexible shared records; detailed requirement assessments and applied controls already exist in dedicated assessment screens. A coherent workspace requires connecting those genuine objects, not only styling generic JSON fields to resemble a fully native SSP. [Shared record engine](/Users/tkhan/IdeaProjects/ciso-assistant-community/apps/web/src/features/modules/SharedModuleWorkspacePage.tsx:3643), [Assessment detail](/Users/tkhan/IdeaProjects/ciso-assistant-community/apps/web/src/features/assessments/ComplianceAssessmentDetailPage.tsx:1).

### 3. Reusable narratives and inheritance: preview the effect of reuse

The reusable implementation library should distinguish a general capability statement from a system-specific override. Each reusable item has a stable ID/version, owner, referenced components/parties, applicable requirement mappings, last review and affected systems. A system chooses whether to link a reviewed version, inherit a provider portion, add a customer portion, or copy into an independent draft. The UI explains the different update behavior at the choice point.

Inheritance review shows source system/provider/authorization and version, compatible baseline/control IDs, inherited versus retained responsibility, supporting evidence, validity/expiry and known exclusions. Before accepting, show per-control additions, updates, conflicts, unchanged items and unresolved references. Acceptance records who/when/why and the source version. Source changes produce an **Upstream change needs review** queue item; they do not overwrite approved local text or silently claim continued inherited coverage.

Narrative smart references resolve by record identity, not display-name matching. A renaming can update current display text without altering a historical approved snapshot. Missing/deleted/moved references appear as unresolved with the historical name and identity, and block any affected package claim until resolved or explicitly excluded. Context variables (system name, organization, relevant parameters) display their resolved values in Preview; unresolved values get direct repair links.

Import existing SSP → retain original artifact/source location → parse proposed references/statements → compare original/draft → select reusable versus system-specific content → accept selected changes → review dependent-control changes. Deduplication shows both candidates and mappings; do not erase original provenance when consolidating language.

**Current fit:** policy-builder profiles queue catalog controls and create requirement metadata; locally imported/manual profiles are session state. RegML's Apply currently accepts a session attempt without writing a domain narrative. The interface should say **Accept draft** for that operation until a reviewable domain-writeback implementation exists. [Policy queue](/Users/tkhan/IdeaProjects/ciso-assistant-community/apps/web/src/features/ai/AIPolicyBuilderPage.tsx:498), [RegML apply](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/services/ai/regml.ts:1125).

### 4. Evidence detail: provenance, population and lifecycle

The evidence library offers filters for system/control/provider/source account/type, review state, observation window, stale/unknown coverage and owner. Avoid a single mixed “Evidence” list that treats an uploaded policy, scanner finding, API snapshot and assessment assertion identically. The user-facing type indicates what the artifact represents; backend storage details belong in administrative diagnostics.

Evidence detail tabs: Preview, Coverage, Collection, Review, Usage, History. Preview exposes the actual file/content safely and states unsupported preview rather than substituting a placeholder. Coverage identifies controls/objectives, required population, collected population, exceptions/out-of-scope reasons and completeness. Collection gives provider and connection identity, source account/region/environment, resource IDs, collection/observation times, method/rule version, run ID, original source link and receipt. Sensitive request headers/credentials remain redacted; external reviewers get only the allowed evidence view.

Usage shows every system/control/assessment/package using this version; “reuse” links a version and purpose, not duplicated uploads. Review names reviewer, purpose, result, notes and accepted version. History preserves prior versions and collector runs. Hash/integrity display is meaningful only when computed and verified; a badge cannot infer it from a filename.

New file/reference → draft version → verify required metadata/preview → map to scoped objects → submit for review → accept or request changes. A replacement does not hide the current accepted version. The uploader can save draft without asking for acceptance; acceptance establishes a specific review, not regulatory approval. Evidence freshness uses observed/effective time and cadence, while failed collections retain the age of the last successful evidence and mark the current failure.

**Current fit:** evidence sources/jobs/assurance already supply durable artifact and run concepts. Questionnaire “uploads” and portal evidence notes currently carry reference text only. Their forms must label **Evidence reference** until a real upload/linking path is present. [Questionnaire renderer](/Users/tkhan/IdeaProjects/ciso-assistant-community/apps/web/src/features/builders/QuestionnaireResponsePage.tsx:209), [Portal response](/Users/tkhan/IdeaProjects/ciso-assistant-community/apps/web/src/features/portal/PortalAssignmentDetailPage.tsx:259).

### 5. Reviews and decisions: recognize exactly what is being accepted

Use a shared review layout with Context, Change summary, Source/evidence, Decision and History. The header states the object/version/scope and why it needs review. Reviewers can approve/accept the relevant version, request changes with a specific comment, or defer with an owner/date/reason. Required reasons apply to substantive decisions and exclusions, not every benign edit. Ordinary reversible edits should remain efficient.

Decision review shows a before/after diff and affected controls/systems/packages. Current review must be bound to an immutable version or equivalent concurrency token; if the source changes during review, the UI identifies the change and requires review of the new version. A successful dialog close is not a saved decision: show the server-confirmed actor/time/version and update the queue only after acknowledgement.

Keep internal discussion distinct from assessor-facing comments and external sharing. **Share for assessor review** lists recipient(s), visible objects and snapshot versions. The external person sees their allowed scope, can request changes or submit their result, and cannot accidentally edit tenant-wide source controls. Do not grant broader permissions merely because a person is assigned.

**Current fit:** assurance review decisions and questionnaire instance transitions offer real foundations. Portal saves currently reload the complete draft map, which can discard unsaved edits on other requirements. Preserve each draft independently, and warn before a transition that would invalidate/discard unsaved answers. Fix anonymous questionnaire routing before relying on it for external collection. [Portal save/reload](/Users/tkhan/IdeaProjects/ciso-assistant-community/apps/web/src/features/portal/PortalAssignmentDetailPage.tsx:49), [Anonymous route defect](/Users/tkhan/IdeaProjects/ciso-assistant-community/apps/web/src/shell/AppLayout.tsx:404).

### 6. Reports, packages and exports: show the actual deliverable

The system package workspace lists SSP/system plans, SAP, SAR, POA&M, inventory, diagrams/agreements, referenced evidence and program-specific supporting deliverables. Package contents are versioned entries: Generated, Uploaded, Referenced, Missing, Excluded with reason. The generation profile specifies template/version, framework/baseline edition, system/scope, observation date/window and required formats. A contents preview names actual files, validation results and unresolved prerequisites.

Generation uses a stable input snapshot and returns a manifest including source IDs/versions, generation time, template/profile, output types, validation profile/results and actual file sizes/digests where implemented. **Generate preview** and **Generate deliverable** are different actions. A .docx/.xlsx filename cannot imply a native document; a supported-format badge requires file inspection and representative content validation. OSCAL success requires the actual selected OSCAL model/version/schema/profile checks, not merely well-formed XML.

Export states are honest: Not available (with prerequisites), Preview only, Generating, Generated with validation results, Failed, or Superseded. A blocked export points directly to the missing categorization/parameter/attachment/review. Display required manual work and exclusions before submission. A download action must point to an existing artifact; preserve a generated snapshot after source records change and clearly mark when it no longer reflects current data.

Reports show exact record count and filter logic. Zero matching records remains zero; sample data is confined to an explicitly separate demo. Clicking a metric/table/chart segment opens the exact filtered record set. A dashboard tile renders real scoped data or says unavailable; the screen never labels descriptive text a live report. Share/subscriptions state whether a definition was saved, an artifact generated, a send queued, delivered, or failed; those events are not interchangeable.

**Current fit:** Report Builder's zero-data/sample and zero-match/unfiltered fallback must be removed for operational reporting. Its “Bar/Line/Pie” preview currently uses one horizontal-bar representation. Dashboard preview is descriptive text. Export Builder tests generate semantic previews; AI compliance exports produce metadata/simple XML/text, sometimes with native-file extensions. These existing operations should be relabeled until native deliverable support is implemented and tested. ### 7. Automation and AI: bounded effects, reviewable results

Start from a task (“collect cloud configuration”, “draft this narrative”, “create remediation tickets”), not a generic Run button. The setup identifies provider/connection identity, scope/account/system/resources, read or write behavior, cadence/trigger, destination and accountable owner. Preview lists affected objects, anticipated changes, skipped/unsupported inputs and maximum work. Execution limits can cover item count, time, external calls or permitted action types; they are actual enforced bounds, not decorative fields.

A run detail shows inputs/version, start/end, scope and coverage, completed/skipped/failed items, produced artifacts, proposed changes and actual external write receipts. Retry only failed/retryable items with deduplication and preserved history. Pause/cancel states truthfully explain already-completed effects. A stopped connector keeps prior accepted evidence and flags collection freshness; no automatic green reset.

AI drafts identify source artifacts/versions and available context. Unsupported statements are flagged for review; confidence is only displayed if it has a defined/calibrated meaning. The comparison view can accept individual passages/changes, preserve edits and reject suggestions. A source prompt/reference is untrusted material, not approval to act. Applying a narrative or creating a ticket presents the exact destination and before/after record effect. Authorization/risk acceptance is never an automatic agent outcome.

**Current fit:** the Integration Manager test/sync path is deterministic dry-run metadata, distinct from actual GRC/AWS collectors. Response Automation uses a fixed question bank rather than arbitrary uploaded-questionnaire parsing; require a supported intake format and parsing preview before promising uploaded-document answering. RegML Apply is session-level acceptance; there is no general approved narrative writeback through that action today. Keep enabled/configured/last verified/last successful and running states separate. ### 8. Builders and administration: configuration behind the operating task

Form/rule/questionnaire/export/dashboard/wayfinder builders remain a distinct admin/library area. Analysts operate an approved template, rather than being dropped into the authoring control plane. Template lifecycle is Draft → Validated → Published version → Retired, with validation referring to explicit tests/constraints. A published version used by active assessments/responses remains pinned until a deliberate upgrade review explains changes.

Field types supported by schema must have honest runtime rendering; multi-select, tables, dates/numbers and file upload need corresponding response widgets and validation. The same rules must affect visibility/required/disabled behavior in preview, internal responses, external responses and API saves. Publish review states affected systems/templates/records and compatibility breaks. Import/export/reset identifies exactly which configuration changes, preserving unrelated records and approved versions.

Admin screens separate saved preferences from verified runtime enforcement. SSO/MFA/service-account/readiness panels show actual supported methods and verification events; a policy checkbox cannot establish that a login challenge or API credential verifier exists. Credential tokens must not appear usable until authenticated calls validate them. No proposed visual redesign should paper over those implementation gaps. Branding/general settings should show which surfaces actually consume a preference, without promising global behavior from an isolated preview.

**Current fit:** Form Builder and shared records enforce many rules, but questionnaire renderers reduce some types to text. Setup MFA persists a policy and service accounts persist token inventory/prefix data without verified credential authentication. Address these as distinct implementation requirements, not UI-only cleanup. ## Saved views, source identity and approval ergonomics

Saved views are a proposed product feature across queues, controls, evidence and packages. A view saves filters/columns/sort/grouping, permitted scope and optional defaults; it never saves permission elevation. Personal views are private; team views require a named owner and sharing scope. URL deep links reproduce the view/context where permitted and omit sensitive draft text. If referenced systems or filters become inaccessible, show the changed scope rather than silently broadening results.

Source identity is visible at the point of decisions: provider/connection/account/resource IDs, catalog/control/part/version, system boundary, artifact/version/run, statement/reference IDs and external ticket destination. Display names can be friendly, but reconciling by names alone must not merge unrelated sources. Object inspection reveals the exact identity and lineage without exposing secrets or internal infrastructure unnecessarily.

Approval ergonomics use explicit buttons on the reviewed object and a concise, complete summary. Avoid full-screen confirmations for every ordinary save or harmless filter change. Use confirmations for irreversible deletion, external sharing/write effects, publishing/retiring versions, applying inheritance and recorded acceptance. Disabled actions explain the missing permission or prerequisite; a reviewer can inspect the relevant blocker from that explanation. Tooltips supplement visible labels and never contain the only reason for failure.

On narrow screens, the selected task stays visible while detail is a full-height sheet; essential decision/context is above long secondary metadata. Tabs wrap or scroll without hiding the current state. Modals/drawers trap focus, return focus, and close with Escape when safe; unsaved changes get an explicit choice. Tables have semantic headers and keyboard reachable actions; status uses text/icon as well as color. Dense desktop tables preserve internally scrollable columns and do not force tiny text.

## Implementation boundaries and acceptance evidence

The desired full-suite design should be expressed as multiple vertical implementation slices behind one coherent UX. These are proposal priorities, not an authorization to independently change APIs, persistence or access control.

| Scope-preserving queue + record review | `shell`, `ops`, `assurance`, shared modules | Selected system/filters survive drill-in/back; counts reflect accessible matching records; changed-object review prevents stale approval; no draft loss. |
| Evidence provenance/lifecycle/coverage | `evidence`, `assurance`, questionnaire/portal | Real artifact/reference transport; current/draft/superseded versions distinguishable; collection gaps remain visible; evidence usage/version shown in package. |

Report design validation separately from functionality: a screenshot can show a well-composed queue while proving nothing about persistence, export validity, collector credentials or authorization decisions. Representative end-to-end scenarios should cover a new system, inherited provider controls, stale evidence, failed collection, narrative revision, assessor changes, remediation/retest, package regeneration and an authorization decision recorded from an actual permitted actor.

Measure actionable results: time from assigned item to correct source, duplicate evidence uploads, missing-source references, stale evidence caught before package generation, review turnaround, failed/partial automation visibility, export validation defects and lost-draft events. Establish baselines before setting numerical targets. Do not optimize a completion percentage by hiding unknown/not-applicable/failed items.
