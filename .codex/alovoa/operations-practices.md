Target: `/Users/tkhan/IdeaProjects/ciso-assistant-community`, canonical `apps/web` + `cloudflare`. Reference root has no `AGENTS.md`; target project instructions apply to this report.

**Initial audit boundary:** source/manifests/configuration code were inspected read-only. No secret or environment-file contents were read, and no package install, production/local smoke, deployment, remote schema query, migration or credential verification was executed. Source bodies that load environment files were read as code; those loaders were not invoked. The initial audit created only this analysis document. ## Main finding

Pairara's most useful operational practice is an **evidence ladder**: source wiring inventory → declared outcome proof → actual local test execution → real Worker/D1 readback → explicitly separate external/live evidence. It also supplies concrete endpoint ownership checks, strict operations tooling, local runtime tests, targeted coverage floors, failure artifacts and traceability ledgers. Regovise already has meaningful typechecks, lexical alignment, GRC fixtures, queue-recovery checks and browser-source inventories; those foundations should be composed and strengthened, rather than discarded.

Pairara is not a uniformly safe template. Its release dry-run can still run remote migrations, its shell release path reaches credential/bootstrap/schema operations before the deploy dry-run branch, and its broad local harness has shared run directories and kill-by-port cleanup. Static feature ledgers often check source presence rather than execution. Both repositories use mutable CI action tags and neither inspected deploy workflow promotes a single immutable previously tested bundle. Port the useful principles while rejecting these concrete defects.

## Actual reference command and ownership structure

The root Pairara `package.json` owns named verification commands, Node/npm engine constraints and the npm workspace list. The Worker/mobile/shared packages use the root installation; React 18 web retains a separate dependency tree. `verify:pairara-regression-readiness` chains quality policies, operations typecheck, lint/security checks, contracts/mobile parity, action outcome tests, web/Worker tests, agent audits, architecture/traceability/lineage and a local browser harness. CI additionally runs several web/mobile checks before that chain, so some work is repeated. Production-smoke commands are separate but have many aliases. Regovise has no root package manifest today. Its canonical checks live in separate `apps/web/package.json` and `cloudflare/package.json`; the repo also contains independent legacy manifests. An operations runner can compose those canonical commands from one documented root entry without changing workspaces, React versions, public APIs or deployment topology. A root npm workspace migration is not a prerequisite and should not be inferred from Pairara's arrangement. Pairara's source-facing operations have cohesive directories: `ops/quality` for deterministic policy checks, `ops/audit` for inventories/ledgers, `ops/lib` for reusable source/path helpers, `ops/local` for local runtime orchestration, `ops/evidence` for run evidence assembly, `ops/security` for verified dependency remediation and `ops/release` for cloud-affecting operations. Keep that responsibility separation; do not mechanically relocate every Regovise script or copy dating/mobile/payment features.

## Specific reference behaviors to reject or change

1. **Dry-run cloud effects.** Pairara release YAML can still apply remote migrations when `dry_run=true`; the shell path sources production configuration, verifies credentials, bootstraps resources and may apply migrations/query production schema before skipping deployment. The initial Regovise snapshot had the same migration-guard defect in both YAML and shell; the implementation below fixes the assigned paths. Target YAML line 120 was the original offending condition; the implementation below adds the dry-run guard. Guarding only deployment does not make the whole operation a dry-run.
2. **Implicit production environment or credentials in local work.** Pairara broad harness runs local Wrangler with the normal Worker config and inherited ambient process environment. Target `prepare_local_dev_vars.mjs` reads `.env-prod` and copies the bootstrap secret into `.dev.vars`; if it writes, its output contains only the managed keys and can drop other existing keys. Do not use that preparation path for an isolated test runner. [T · cloudflare/scripts/prepare_local_dev_vars.mjs:33](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/scripts/prepare_local_dev_vars.mjs:33) [T · cloudflare/scripts/prepare_local_dev_vars.mjs:49](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/scripts/prepare_local_dev_vars.mjs:49)
3. **Shared run state and killing unrelated processes.** Pairara shell local harness uses one `.run` directory/PID file, unconditionally resets its persist path, and calls `free_worker_port` which sends kill/SIGKILL to whoever owns that port. Port selection reduces but does not remove races. Per-run temp state and owned process cleanup are required. Its smaller native-runtime test is a better starting pattern.
4. **Silent test-navigation repairs.** `history.pushState` and forced clicks can hide broken real navigation. Route reachability, screenshot capture, UI click outcome and persisted result are different proofs.
5. **Static `covered` or source-token counts as runtime pass.** Reference feature verification and lineage mainly check references. The outcome runner and actual local tests are the evidence of execution. No static catalogue should label provider credentials, external callbacks, native document formats or all actions verified.
6. **Freshness without revision/target identity.** “Latest report” by timestamp/mtime can bind the wrong run, and the evidence catalogue's production URL comes from current environment/default rather than checking each report's verified target. Bind evidence to exact revision/profile/origin and preserve unknown provenance. [A · ops/evidence/buildPairaraFeatureEvidence.ts:539](/Users/tkhan/IdeaProjects/alovoa/ops/evidence/buildPairaraFeatureEvidence.ts:539)
7. **Regex rewriting of migration SQL after partial failure.** Removing transaction wrappers/ADD COLUMN statements to continue can obscure migration state and assumes SQL formatting. Use the target's real migration mechanism/history and tested idempotency policy rather than transplant that workaround.
8. **Mutable action tags, implicit permissions and rebuilt deploy artifacts.** These are omissions in the reference, not best practices. Action version numbers alone do not prove supply-chain identity; promotion should use exact tested bytes.
9. **Unbounded aggregate scripts and duplicate work.** The reference aggregate repeats web/Worker checks, some child processes have no timeout, and many production aliases obscure side effects. One explicit command graph with scoped checks, bounded execution and per-step receipts is clearer.
10. **Blind TypeScript/structure/ignore policy copying.** The target intentionally contains Python/Svelte/reference code and existing JS tooling. Do not restructure workspaces, globally ban all JS, add mobile contracts, ignore all `.codex` work or force dependency patches simply to pass a transplanted policy.

## Report and artifact contract to implement

A useful verification receipt should carry: run ID; source commit plus dirty-tree fingerprint when relevant; selected check/feature/control IDs; exact command/cwd/tool versions; start/end/duration; target type/origin and deployment identity where available; config/fixture/schema/profile version; per-step passed/failed/skipped/blocked/timed-out outcomes; assertions/readbacks; artifact paths/digests; cleanup status; external boundaries; and explicit limitations. Logs must exclude tokens, cookies, secret/header values and real client data.

Static declared proof, local outcome execution, local persistence, external-provider execution and approved live evidence are separate fields.
