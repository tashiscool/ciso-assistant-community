# Pairara backend practices transferable to Regovise

Audit date: 2026-10-11 (America/New_York). Reference: `/Users/tkhan/IdeaProjects/alovoa`, now named Pairara, especially `apps/edge-worker` and `packages/contract`/`api-client`. Target: current Regovise canonical `cloudflare` source plus the earlier [backend map](/Users/tkhan/IdeaProjects/ciso-assistant-community/.codex/maps/backend.md), [risks](/Users/tkhan/IdeaProjects/ciso-assistant-community/.codex/risks.md) and [ATO contract gaps](/Users/tkhan/IdeaProjects/ciso-assistant-community/.codex/design/ato-operations-and-gaps.md). This is a source audit and implementation catalog, not an assertion that either production deployment runs the reviewed tree or that reference tests passed during this audit.

Only this report was written. No reference product code, credentials/private env files, logs containing user data, production endpoints, live provider scripts, database operations or migration commands were accessed/run. Reference `AGENTS.md` was absent; its `.codex/architecture.md` and source ownership READMEs provided orientation, then code/test sources supplied the evidence. Existing target changes were preserved.

## Outcome

Pairara has useful concrete practices in provider seams, explicit outcome types, mutation-intent policy, guarded D1 state transitions, event outbox/queue dedupe, dead-letter integrity and replay claims, session eligibility/revocation, environment-specific credentialed CORS, response security/cache policy, bounded background fanout and isolated regression testing. Regovise already implements parts of several of these, notably D1 bound SQL, scoped roles, evidence/ConMon job leases, R2 manifests, job/event histories, OIDC validation, PBKDF2 credentials, transactional email timeout/dedupe, Jira approval and the separate service-delivery runtime.

The correct transfer is **the invariant and its tests**, not copying Pairara's dating/business data, thresholds, credentials, smoke exceptions, monetary caps, user IDs, route names or deep class inheritance chain. Several claimed reference conventions are incomplete in its actual code; those limitations are recorded below.

## Priority and authorization notation

- **P1:** identity, access, irreversible side effects or serious loss/corruption/replay correctness; source-backed conditional risk, not confirmed production exposure.
- **P2:** common-path reliability, bounded execution, input/contract integrity, truthful state, observability and useful regression coverage.
- **P3:** scoped maintainability/performance improvement after correctness.
- **N:** ordinarily safe bounded internal reliability/tests/docs, with existing valid-input API/authorization/persistence meanings preserved; no new dependency. Root still chooses an implementation slice.
- **C:** contract/architecture/public API/state/schema/scheduling/retention/budget policy changes require review and approval under target instructions.
- **S:** auth/access/encryption/secrets/audit behavior needs explicit sensitive-change authorization and isolated tests, even if technically small.
- **O:** external deployment, remote migrations, provider credentials/usage or live operations are outside this source audit and require the appropriate authorization.

No table below authorizes a protected change. Broad user intent to adopt best practices supports doing the safe work and preparing concrete protected patches; it does not justify silently choosing a new domain architecture or running production operations.

## Practices already present in Regovise: retain and test

- `router.ts` already centralizes service dispatch and typed error shaping; `utils/http.ts` correctly preserves custom JSON response headers/status and 405 Allow values. Adopt additional validation without silently breaking custom envelopes.
- Bound SQL, tenant/domain role assignments and scoped filters are widespread. The known root/admin/grant/session exceptions are targeted gaps, not a reason to discard all authorization code.
- Evidence/ConMon consumers share process functions with inline replay, use terminal success checks and tenant DO leases, write raw/normalized R2 artifacts and job coverage/error status. Their lease-held/missing-job acknowledge policy still needs a recovery contract.
- GRC has schema/manual validation, content hashes/provenance, bounded known message variants and explicit queues; unsupported fallback/crosswalk coverage must stay truthful.
- The service-delivery runtime already demonstrates case version matching, artifact SHA256 checks, intent idempotency, outbox/recovery and Stripe receipt matching. It is an imported generated runtime: use its recorded upstream/version rather than hand-editing the bundle without an approved update workflow.
- OIDC already verifies token signature/JWKS/issuer/audience/nonce with PKCE; local passwords already use PBKDF2 and lockout. Pairara authentication code is not a replacement spec for these established target flows.
- Email already has configurable real providers, native timeout, dedupe, provider request ID/status delivery logs and branded templates. Improve the shared transport behavior without erasing dedicated delivery observability.
- Jira uses approved drafts and stored integration run outcomes. Its external action contract deserves replay/ambiguous-result tests before adding generic automatic retries.

## Important reference limitations: do not transfer as “best practice”

1. **Deep inheritance remains the domain architecture.** The reference core README explicitly says feature/core files are links in one class chain, can call methods elsewhere through `this`, and rely on implicit extends order. File separation is not genuine independent service isolation. Do not import this chain into Regovise.
2. **Timeout helper bounds headers, not complete body consumption.** Its timer is cleared as soon as fetch returns Response and it replaces `init.signal`. A hung `response.json/text` can outlive that deadline. Several providers still call plain providerFetch, including Spotify, Turnstile, external AI and verification/media. Correct these limits in the target helper instead of treating every call as already bounded.
3. **Queue schema parser is not exhaustive.** Known event discriminator/base shape is checked, but most variants are cast without payload-specific required-field validation. Payment/native variants have deeper guards. New Regovise validation must cover each actual message contract.
4. **Queue in-progress and missing-table behavior needs recovery design.** The reference wrapper can return in_progress; consumer ignores returned status and acknowledges. It has no general stale-claim recovery in that wrapper, and missing dedupe table processes without protection. Target evidence/ConMon held lease currently has analogous risk; do not duplicate it.
5. **HTTP replay is not a universal exactly-once or authorization guarantee.** The wrapper does not compare explicit-key payload mismatch, replays body/status without every original header/cookie, does not reauthorize its cached result, and handles expired/failed records by calling the handler without a fresh atomic claim. The mutation policy appropriately excludes several domain-owned paths, but target design must fix remaining invariants.
6. **Outbox needs receiver idempotency.** Send-success followed by failed mark-dispatched can cause another send; arbitrary unique event insertion is not full exactly-once external effect. The missing-table send fallback explicitly loses durable staging.
7. **No demonstrated universal request tracing/error wrapper.** Source has structured event logs and provider/job trace IDs, not one global request ID pipeline. The Worker fetch path largely delegates without a universal try/catch. Target should retain its useful catch boundary and improve safe error contracts deliberately.
8. **Budget checks are not reservations.** Read projected spend then record spend can race concurrent calls; fallback default caps are application-specific; `enabled=0` bypasses cap enforcement, not necessarily provider disablement. Do not copy defaults or claim a strict concurrent ceiling without reservation logic.
9. **Truncation/property-name redaction is incomplete.** Provider raw error body snippets and scalar/free-text receipts can still contain private content; a regex matching key names does not sanitize all evidence. Target must choose protected logging/storage behavior and tests.
10. **Shadow GET is not automatically harmless.** Reference forwards request headers to configured legacy origin and does not bound its fetch; Regovise GET may seed/backfill. Audit egress/read effects before any cross-runtime comparison.
11. **Reference CSP and HSTS are product policy, not universal settings.** Broad HTTPS/connect sources, unsafe-inline and two-year includeSubDomains/preload values do not establish the best CSP for Regovise, and may break authorized embedding/integrations.
12. **Retention and scheduler values are business choices.** Seven/thirty-day cleanup and dating reminder windows are inappropriate defaults for regulatory evidence, signed decisions, review records or agency obligations.
