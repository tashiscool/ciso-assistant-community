## 2. Identity and permission model

[auth.ts:21](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/auth.ts:21) resolves a D1 session from `ca_session` or legacy `session_id` cookies, verifies the expiry, and attaches tenant/user IDs. [session.ts](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/session.ts:1) creates UUID sessions with a seven-day TTL, stores IP/user-agent metadata, and builds cookies with HttpOnly, SameSite=Lax, Path=/, and Secure for secure requests. An invalid session falls back to header identity where allowed. A bearer value here is treated as a user identifier for development/exchange identity, not verified as a JWT.

Ordinary header identity (`x-tenant-id` and `x-user-id` or `Bearer <user id>`) is enabled outside production. **The session-exchange route is an explicit production exception.** This is significant and should be reviewed before assuming production identity is possession-verified; see findings below.

Core login routes at [core/http.ts:7710](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/services/core/http.ts:7710):

| API under `/_api/core` | Behavior |
| --- | --- |
| `bootstrap/status` GET | Reports first-workspace initialization state. |
| `bootstrap/initialize` POST | Requires bootstrap secret, validates tenant/admin input, creates first tenant/principals/config, issues session; refuses already-initialized workspace. |
| `bootstrap/admin-session` POST | Bootstrap-secret assisted recovery/session for matching local-login tenant admin. |
| `login/config`, `login/options` GET | Initialization, email-code, tenant and configured SSO sign-in options. |
| `login/request-code`, `login/verify-code` POST | Normalized email and tenant lookup, ten-minute hashed code, request rate limits, attempt/expiry/used checks, actual email provider or nonproduction preview, then session issuance. |

[core/oidc.ts:419](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/services/core/oidc.ts:419) exchanges the code with discovered token endpoint, verifies identity token signatures through JWKS, expiry, issuer, audience, and nonce; PKCE helpers/start are earlier in the file. SSO configuration also stores claim mappings, JIT provisioning/group synchronization, enforced login, and local fallback. **SAML is configuration-only**: `sso/start` returns `saml_not_active`; Cloudflare Access configuration is front-door protection only, with Regovise sessions still required after entry ([core/http.ts:8320](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/services/core/http.ts:8320)).

The effective permission graph is `tenant → folders(root/domain/folder) → role assignments(scope_folder_id, is_recursive, user_id OR group_id) → roles → role_permissions`, plus user-group memberships. [authorization.ts:135](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/authorization.ts:135) builds the union of a user's direct/group permissions; [loadScopedPermissionContext:194](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/authorization.ts:194) derives accessible folder/domain IDs via descendant expansion. Core domain APIs, evidence, assurance, and agent routes often use scoped permission helpers and filter/query objects by accessible folders. Builders/AI/parts of operations instead use tenant-wide `requireAnyPermission`, so having a permission in one domain is not uniformly equivalent to access to every tenant object. This is an implementation boundary to audit, not a claim of complete isolation.

[IAM handler:1731](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/services/iam/http.ts:1731) supports `me`, folder CRUD/tree context, user CRUD (names, active state, auditee/local login/preference fields), group CRUD/membership, role CRUD/permission lists, and direct/group scoped role assignment CRUD. Built-in role templates and demo users are defined in the same file. `me` combines principal profile, permissions, groups, assignments, folder access, and workspace information for the frontend.

## 14. Source findings and practical limits

These are source-backed concerns, not exploit-tested production findings. They were reported to the root agent without modifying security-sensitive code.

1. **Production session exchange accepts client-selected identity.** [auth.ts:55](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/auth.ts:55) permits header identity at `/core/session/exchange` even production; [core/http.ts:8831](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/services/core/http.ts:8831) only checks selected principal exists/is active before creating a session. No possession proof is visible in that path. External front-door restrictions may mitigate exposure, but are not proven by these functions.
2. **General API credentialed CORS mirrors arbitrary origins.** [utils/http.ts:44](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/utils/http.ts:44) sets supplied origin and allow-credentials. Cookie SameSite=Lax constrains ordinary cross-site cookie transmission, but does not make this allowlist-free CORS policy equivalent to a fixed trusted-origin policy.
3. **“Root admin” guard is not root scoped.** [authorization.ts:362](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/authorization.ts:362) loads a root folder, but loads permission context without `scopeFolderId` and accepts any administrative permission from the user's tenant-wide union. A domain-scoped admin role can therefore appear sufficient for tenant admin surfaces. The service-delivery adapter separately requests root-scoped permissions.
4. **Trust-center grant not tied to requested artifact offering.** [loadArtifactPayload:5336](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/services/fedramp/runtime.ts:5336) loads artifact by ID and, when any grant/token pair is supplied, validates that grant then bypasses tenant-admin branch; it does not compare grant tenant/offering to artifact tenant/offering. A valid grant from a different offering appears sufficient for a known nonpublic published artifact ID.
5. **Tenant workflow snapshots lack a complete identity guard.** [core/http.ts:14829](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/services/core/http.ts:14829) rejects a mismatched tenant only if `ctx.tenantId` exists; an anonymous request with tenant ID in path reaches the DO snapshot. Confirm whether external deployment policy prevents this exposure.
6. **Fresh demo bootstrap orders child records before tenant.** [bootstrapDemoTenant:5593](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/services/core/http.ts:5593) calls IAM seed before tenant insert runs; [IAM seed:1440](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/src/services/iam/http.ts:1440) inserts folders referencing tenant-demo immediately; [0003](/Users/tkhan/IdeaProjects/ciso-assistant-community/cloudflare/migrations/0003_workspace_admin.sql:1) enforces folder tenant FK. This explains a fresh migrated local bootstrap FK failure reported by the root agent. No product fix was made.
7. **Apparent completed/healthy states sometimes mean metadata or preview.** Integration test/sync, export builder, generic compliance formats, quantitative simulation refresh, RegML Apply and MFA/service-account administration have the concrete limits documented above. UI labels/success states should not be read as provider verification/native rendering/domain mutation.
8. **Reads can write defaults/backfills.** Core assessment details, builders, integrations, setup and FedRAMP snapshots can lazily seed/backfill data. GET-only UI exploration against production is not automatically read-only at persistence level; this map uses local source, not production exploration.
9. **No universal request transaction/audit pipeline.** Multi-step D1/R2/DO/queue operations commonly commit pieces sequentially, use separate state updates, and log follow-up failures. Dedicated event/review/access/agent ledgers exist, but `index/router` has no global write-audit middleware. Failure/retry can leave partial artifacts/state; specific critical paths need targeted verification.
10. **Catalog declarations do not certify feature completion.** Semantic coverage/registry badges/parity snapshots/README descriptions combine implementation descriptions and curated status. Confirm behavior through actual handler/runtime path and isolated tests before stating complete parity with the original product or regulated deliverables.
