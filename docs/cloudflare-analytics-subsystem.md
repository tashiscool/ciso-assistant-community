# Cloudflare Analytics and Reporting Subsystem

## Section A: Assumptions

1. `APP_NAME` is `CISO Assistant Community`.
2. The platform is multi-tenant and every write/query path must remain tenant-scoped.
3. The existing command pipeline is the canonical event producer: `command-worker -> domain_events -> events-q`.
4. The 165 Django models already indexed into `canonical_model_registry` are the source of truth for model metadata during migration.
5. Compliance constraints are FedRAMP Moderate, NIST 800-53 evidence traceability, least-privilege tenant isolation, and PII minimization.
6. Default sizing assumptions for this subsystem are:
   - ingest peak: 250 events/sec
   - daily volume: 5 million events/day
   - ingest p95 target: under 150 ms from API receipt to queue acknowledgement
   - dashboard p95 target: under 300 ms from edge query to JSON response
7. Retention defaults are:
   - hot: 30 days in D1 minute-level + dedupe state
   - warm: 180 days in D1 hour-level rollups
   - cold: 730 days in D1 day-level rollups + R2 raw NDJSON replay history
8. Time semantics are UTC in storage. Currency is not modeled in this slice.
9. Raw events are immutable and replayable from R2. D1 is strictly for read-optimized projections and checkpoints.
10. Cloudflare R2 lifecycle rules should be configured in the dashboard to mirror the cold retention window for `ciso-analytics-raw-r2`.

## Section B: Architecture and Data Model

### Recommended architecture

1. `edge-api-worker` handles lightweight ingest and query APIs.
2. Direct analytics ingest uses `POST /api/v2/analytics/events` and only validates, normalizes, enqueues, and acknowledges.
3. Domain activity generated by the rest of the platform already flows through `events-q`; the new analytics worker consumes that same immutable stream.
4. `analytics-worker` performs async aggregation only after the queue delivery succeeds.
5. `AnalyticsAggregateDurableObject` is keyed by `tenant_id + UTC hour bucket` and provides per-shard serialization so concurrent queue batches cannot double-increment the same counters.
6. Raw event shards are written to R2 as NDJSON files under `analytics-raw/{tenant}/{yyyy}/{mm}/{dd}/{hh}/...`.
7. D1 stores:
   - dedupe records
   - raw shard metadata
   - 1-minute, 1-hour, and 1-day event rollups
   - daily domain/source/model activity tables
   - checkpoints and rebuild run metadata
8. Dashboards query rollup tables only. No raw R2 scans are used in hot paths.

### Failure handling

1. Duplicate events are ignored through `analytics_event_dedupe` keyed by `(tenant_id, event_id)`.
2. Queue processing failures go to `dead-letter-q` with the offending payload and shard context.
3. Durable Object ingest failures fail the whole shard batch and keep the failure visible in DLQ instead of partially applying counts.
4. If R2 write succeeds but D1 batch fails, the message is sent to DLQ and the raw shard key is recoverable from the DO response/logs for replay.
5. Checkpoints are updated only after the shard is durably written to R2 and projected into D1.

### Data model summary

1. `analytics_event_dedupe`
   - idempotency + replay visibility
   - stores `raw_object_key` once the event is projected
2. `analytics_raw_shards`
   - one row per R2 NDJSON object
   - maps replayable raw storage to shard/hour metadata
3. `analytics_rollup_1m_event_volume`
   - short-range dashboards and burst analysis
4. `analytics_rollup_1h_event_volume`
   - medium-range trend queries
5. `analytics_rollup_1d_event_volume`
   - long-range reporting by event type
6. `analytics_rollup_1d_domain_activity`
   - cross-domain operational reporting
7. `analytics_rollup_1d_source_health`
   - source quality/error-rate monitoring
8. `analytics_rollup_1d_model_activity`
   - migration visibility for the 165 Django models through canonical model keys
9. `analytics_checkpoints`
   - queue processing and retention run checkpoints
10. `analytics_rebuild_runs`
   - auditable replay/backfill bookkeeping

### API contracts

1. `POST /api/v2/analytics/events`
   - accepts one event object or `{ "events": [...] }`
   - required fields per event: `event_id`, `tenant_id`, `source`, `event_type`, `event_version`, `event_time`, `ingest_time`
   - response: `202 Accepted` with queued event IDs
2. `GET /api/v2/analytics/overview`
   - returns totals, active sources/domains/models, top event types, and latest checkpoint for a tenant/range
3. `GET /api/v2/analytics/volume`
   - returns rollup volume by `grain=1m|1h|1d`
4. `GET /api/v2/analytics/domains`
   - returns highest-volume domains over a range
5. `GET /api/v2/analytics/sources`
   - returns per-source total/error counts
6. `GET /api/v2/analytics/models`
   - returns model activity joined to canonical registry metadata
7. `GET /api/v2/analytics/checkpoints`
   - operational visibility into queue and retention checkpoints

### Queue and DO behavior

1. `events-q` is the single write-once analytics stream.
2. `analytics-worker` deduplicates each event before aggregation.
3. The worker groups events by `tenant_id + event hour` and sends each group to the DO.
4. The DO:
   - validates shard consistency
   - writes NDJSON to R2
   - updates D1 rollups in one batch
   - returns the raw object key and flush metadata
5. The worker then updates dedupe rows with the R2 shard pointer and advances checkpoints.

### Retention and compaction

1. The analytics worker runs a daily cron at `03:15 UTC`.
2. Automated cleanup removes:
   - dedupe + 1-minute rollups after hot retention
   - 1-hour rollups after warm retention
   - 1-day rollups and raw shard metadata after cold retention
3. Physical raw object deletion should be handled by the R2 lifecycle policy for the analytics bucket.

### Rebuild procedure

Recommended rebuild path:

1. Enumerate objects in `ciso-analytics-raw-r2` under the relevant tenant/date prefix.
2. Insert a row in `analytics_rebuild_runs` with status `requested`.
3. Stream each NDJSON object, normalize each event, and re-enqueue onto `events-q` or replay directly into the DO in order.
4. Update `analytics_rebuild_runs.replayed_events`, `cursor`, and final `status`.
5. Validate by comparing D1 rollup windows before/after replay.

This is intentionally version-friendly because the raw payload and `event_version` are preserved in R2.

## Section E: Risks and Mitigations

1. D1 write amplification
   - Mitigation: roll up in the DO per shard and batch statements; avoid querying raw tables for dashboards.
2. Duplicate delivery from queues or retries
   - Mitigation: `analytics_event_dedupe` with `(tenant_id, event_id)` primary key.
3. Partial shard writes across R2 and D1
   - Mitigation: DLQ failures, raw shard metadata, and replayable NDJSON.
4. Tenant data leakage
   - Mitigation: tenant_id required on every query path and enforced in every primary key/index pattern.
5. Cardinality explosion from event types or model keys
   - Mitigation: daily model/domain/source summaries plus retention trimming; avoid arbitrary dimension fan-out in the first cut.
6. Long-range query slowdown
   - Mitigation: multi-grain rollups and dashboard reads against day/hour tables only.
